## 1. What does this do?

Walk through what happens when the uploader sends `PutObject` with `If-None-Match: *` for a snapshot key, in each of three cases: the key is new; the key already holds those bytes; and another uploader is writing the same key at that moment.

**Your answer:**

>

<details>
<summary>Model answer</summary>

- **New key:** S3 stores the object and returns `200`. Fetch-log outcome `written`.
- **Already stored:** S3 refuses and returns `412 Precondition Failed`. Because the key *is* the content hash, an existing object means the same bytes are already safe, so this is logged as `duplicate` and counts as **success**. Nothing is overwritten.
- **Concurrent write in flight:** S3 may return `409 Conflict`. The uploader retries, and the retry gets `200` (the other write failed) or `412` (the other write won). Either way, exactly one copy is stored.

The key idea: "does it exist?" and "write it" happen as **one atomic step inside S3**, so no interleaving of two uploaders can produce two copies or an overwrite.

**Must mention for full credit:** `200` written; `412` as a successful duplicate because the key is the content hash; `409` retried; why it's atomic.

</details>

## 3. What breaks if…

The ingest uploader used ADR-001's old approach instead: list the S3 prefix, and write only if no file with that hash is listed. Describe a concrete sequence of events where it stores the same snapshot twice, and say why S3's strong consistency doesn't save it.

**Your answer:**

>

<details>
<summary>Model answer</summary>

**A sequence:** the uploader writes snapshot X but crashes before recording success. Systemd or Docker restarts it while a slow retry from the old process is still running, or a backfill job runs at the same time.

1. Writer A lists the prefix and sees no X.
2. Writer B lists the prefix and sees no X.
3. A writes X.
4. B writes X.

With fetch time in the key (ADR-001's format), A and B use different keys, so **two copies** are stored. With the same key and no condition, B **overwrites** A, creating a second version.

**Why consistency doesn't help:** strong read-after-write consistency means a list sees every write that *completed* before it. Here both lists happen before either write. The flaw is that check and act are **two separate requests** (a time-of-check to time-of-use race), and consistency doesn't make two requests atomic. A conditional write does, because S3 performs the check and the write as one operation. List-before-write also costs an extra request on every write.

**Must mention for full credit:** an interleaving where both check before either writes; the result (a duplicate or overwrite); check and act as separate requests; consistency doesn't make them atomic.

</details>

## 4. What breaks if…

Ingest uploads the fetch log at shutdown and again when the hour closes, under one fixed key `bronze/_fetch_log/dt=2026-11-13/hour=10.jsonl`. It restarts at 10:30. What happens to the log for 10:30–11:00, and what does ADR-004 do instead?

**Your answer:**

>

<details>
<summary>Model answer</summary>

At 10:30 shutdown, the file with 10:00–10:30 lines is uploaded to `hour=10.jsonl`, which succeeds. After the restart, the 11:00 close tries to upload `hour=10.jsonl` again, now with the 10:30–11:00 lines. That key exists, so the conditional write returns `412`. The uploader treats `412` as "already stored", so **the 10:30–11:00 fetch log is silently lost**. And if writes weren't conditional, the second upload would overwrite the first and lose 10:00–10:30 instead.

Losing fetch-log lines is serious: the fetch log is how the pipeline tells an outage from a quiet feed (the `unknown` outcome) and how the capture SLO is measured.

**ADR-004's fix:** content-address each upload, `bronze/_fetch_log/dt=…/hour=10/<sha16>.jsonl`. Different content gets a different key, so both uploads are stored. Readers take the union of an hour's files and drop duplicate lines.

**Must mention for full credit:** the second upload gets `412` and is treated as success, so lines are lost silently; why the fetch log matters; content-addressed keys per upload, with readers taking the union.

</details>

## 5. How would you change it to…

ADR-004 chose a bucket-policy deny over S3 Object Lock. Suppose a reviewer insists that bronze must survive even a compromised administrator account. How would you change the design, and what would it cost?

**Your answer:**

>

<details>
<summary>Model answer</summary>

**The change:** enable **S3 Object Lock in compliance mode** on the bronze data, with a retention period. In compliance mode no one, not even the root user, can delete or overwrite a locked object version until its retention ends. A deny policy, by contrast, can be removed by any administrator who can edit the bucket policy.

Practical shape: Object Lock can be enabled on an existing versioned bucket, but it can never be turned off again. A cleaner design is a separate bronze-only bucket with a default retention rule, so `derived/` and `selftest/` stay deletable.

**Costs:**

- It's irreversible: once enabled, Object Lock can't be disabled for that bucket.
- Retention must be chosen up front, and objects can't be removed early, even for a legitimate reason such as a privacy request or a mistakenly archived file.
- Buckets and policies get more complex, and the rebuild drill has to recreate them.
- Optional extras: replicate bronze to a second account that the main admin can't touch, at the price of doubled storage and more IAM.

A strong answer also says which threat each option covers: the deny policy stops bugs and accidents, Object Lock stops a malicious admin, and adding it is an ADR-level change with real downsides.

**Must mention for full credit:** compliance-mode Object Lock (or cross-account replication) as the change; irreversibility and fixed retention as the costs; the threat each option addresses.

</details>
