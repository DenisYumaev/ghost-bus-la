## 1. What does this do?

What exactly does one `trip_updates` snapshot contain, and why are its lines sorted by entity ID?

**Your answer:**

>

<details>
<summary>Model answer</summary>

**Contents:** for every trip ID seen since the previous cut on the 60-second grid, the *latest* message received for that trip, byte-for-byte as received, one message per line, gzip-compressed with a fixed header. That includes today's and tomorrow's trips and any `CANCELED` entries. A trip not seen during the interval is absent.

**Why sorted:** determinism. The server's loop order and reconnects change the order messages arrive in, but the same *set* of messages must always produce the same bytes. Same bytes give the same SHA-256, which gives the same content-addressed S3 key, so a duplicate write becomes a harmless no-op (`412`). Unsorted, two identical fleet states could hash differently and both be stored. A side benefit is that two snapshots can be compared line by line.

**Must mention for full credit:** latest message per entity; bytes unchanged; sorting exists for deterministic hashing and deduplication.

</details>

## 2. What does this do?

ADR-001 says bronze stores "the exact bytes the source returned." What does "raw" mean under ADR-021, and why did it need restating?

**Your answer:**

>

<details>
<summary>Model answer</summary>

**Meaning:** a WebSocket has no single response; data arrives as a stream of separate messages. "Raw" now means *each message's bytes are unchanged*: not parsed and re-serialized, no fields dropped. The framing (which messages are chosen, their order, one per line, gzip) is ours, and it is deterministic and documented.

**Why restate:** ADR-001 was written for HTTP polling, where a response body is a natural unit to store. Without the clarification, someone could argue that snapshotting breaks the raw rule. Worse, someone could "tidy" messages with `json.loads` then `json.dumps`, which silently changes whitespace, key order, and float formatting. The archive would then no longer hold what Metro sent, and parser bugs could no longer be fixed by re-reading bronze.

**Must mention for full credit:** no single response over a WebSocket; per-message bytes unchanged; the framing is ours; re-serializing would violate it.

</details>

## 3. What breaks if…

What goes wrong if the alert detector treats a canceled trip disappearing from the stream as "the cancellation was withdrawn"?

**Your answer:**

>

<details>
<summary>Model answer</summary>

Canceled entries linger for hours after the trip's time (14 of the 22 seen in the probe were already past), and an entry can also vanish for reasons that mean nothing: a dropped connection, a partial snapshot, or Metro pruning old entries. Treating absence as withdrawal would:

- Tell riders "your bus is back" for a bus that is still canceled: a false, harmful message.
- Make the event flap. It closes, then reopens when the entry reappears, which risks a **duplicate alert** and breaks hard rule 4 ("alerts never duplicate").

The correct rule: an event closes **by time**, once the trip's scheduled time has passed. A cancellation is withdrawn only if the trip explicitly returns as `SCHEDULED` before its start.

**Must mention for full credit:** entries linger after the trip; absence has other causes; the false "restored" message or duplicate alert; close by time, withdraw only on an explicit `SCHEDULED`.

</details>

## 4. What breaks if…

The connection drops at 08:00:10 and comes back at 08:00:50, inside one 60-second trip-updates interval (08:00:00 to 08:01:00). What gets written, what gets logged, and what would go wrong downstream if it were logged as a normal snapshot?

**Your answer:**

>

<details>
<summary>Model answer</summary>

**Written:** at the 08:01:00 cut, a snapshot of whatever arrived while connected (08:00:00 to 08:00:10 and 08:00:50 to 08:01:00): the latest message per trip seen in those windows. Something was received, so it is written, not skipped.

**Logged:** the fetch-log row has `partial = true`, and the disconnect is logged separately with its close code and the reconnect time.

**If logged as normal:** downstream would treat 40 unobserved seconds as observed. Any trip missing from that snapshot because its message didn't arrive in time would look like it *left the stream*. Then a vehicle's trip can look like it never ran, so it is classified `missed` instead of `unknown`. That inflates missed-trip numbers, the core finding. It also skews "first seen" times for cancellations (the advance-notice gate) and hides real gaps from the capture SLO. The `partial` flag is what lets the pipeline say "not observed" rather than "absent."

**Must mention for full credit:** a snapshot is still written; `partial = true` plus the disconnect logged; absence would be misread as a real disappearance (`missed` versus `unknown`).

</details>

## 5. How would you change it to…

Suppose the measured day shows trip updates compressing to far more than the storage budget allows. Name two ways you'd change the design, and the cost of each.

**Your answer:**

>

<details>
<summary>Model answer</summary>

Any two, each with a real cost:

| Change | Saves | Costs |
| --- | --- | --- |
| Lower the `trip_updates` cadence (for example 60 s to 120 s) | About half | Coarser "first seen" time for cancellations (worse advance-notice precision), and slower detection eats into the 120 s alert-latency target |
| Store only changes (deltas), with a periodic full snapshot as a keyframe | Large, since most trips repeat unchanged between cuts | Readers must rebuild state; one lost keyframe corrupts a chain; loses "one file = full fleet state"; more code to get wrong in the most important service |
| Compress across snapshots (batch an hour per object), or a stronger codec such as zstd | Large, through cross-snapshot redundancy | Bigger files sit longer in the spool before upload; zstd is a new dependency that needs an ADR; content-addressing per snapshot gets harder |
| Downsample stop-time predictions while keeping every cancellation and status change | Large | Ingest must *parse* to decide what to keep, which breaks "raw bytes" and the rule that ingest stays dumb; lost prediction history can never be recovered |
| Accept the cost and raise the budget | Nothing | Money. S3 Standard is about $0.023 per GB-month, so first check whether "far more" really is |

A strong answer also says: measure first, prefer reversible changes, and record the choice in a new ADR, because ADR-021 decision 3 would change.

**Must mention for full credit:** two distinct changes, each with a concrete cost.

</details>
